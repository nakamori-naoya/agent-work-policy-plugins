# 依存の更新

依存の更新のPR（自動の更新botが作るものを含む）を扱うとき、脆弱性の警告にどう応えるかを決めるときに読む。

## 更新のPRは、最新のbaseで作り直してから検証する

依存の更新のPRは、作られた時点のbaseを基点にしている。そのbaseの後に別のPRが依存を足したり外したりしていると、更新のPRは古い依存の一覧のまま、lockfileやmanifestを整え直した結果を持っている。そのままmergeすると、後から足された依存が消え、baseが壊れる。更新のPRのCIが緑でも、それは古いbaseの上での結果にすぎない。

だから、依存の更新のPRは、mergeの前に最新のbaseで作り直す（更新botに再生成させるか、`update-branch` で取り込んでから、依存の整え直しをやり直す）。作り直した上で必須checkが通ったものだけをmergeする。readinessの `behind_base` は、baseが進んだことを知らせるが、依存の整え直しまではしない。取り込んだだけでlockfileが食い違うなら、整え直しは作業branchの側で行う。

## 到達性の検査と、manifestの警告は別の信号である

脆弱性については、性質の違う二つの信号がある。一つは、脆弱なコードに自分のコードが実際に到達するかを調べる検査である。もう一つは、manifestが指す版に脆弱性が報告されているという警告である。前者は「いま攻撃に使える経路があるか」を、後者は「脆弱な版を使っているか」を答える。

二つを片方で代用しない。到達性の検査が通っても、警告が修正版を示しているなら、上げるか上げないかを決め、上げないならその理由（到達しないこと、上げると壊れる依存があること）を記録に残す。警告が無くても、到達性の検査が失敗したら、それは直す作業である。どちらの判断も、記録が無いと次に同じ警告を見た人が同じ調査をやり直すことになる。

## 判断例（図書館の貸出）

図書館のsiteのrepositoryで、更新botが通信libraryの版を上げるPRを作った。その後、別のPRが外部の認証サービスのSDKを足してmergeされた。更新のPRをそのままmergeすると、依存の整え直しでSDKが外れ、baseのCIが赤になる。最新のbaseで作り直してから、必須checkを確かめてmergeする。

同じlibraryに、利用していない機能の脆弱性の警告が出た。到達性の検査は通っている。修正版へ上げても壊れないので上げる。上げると他の依存と衝突するなら上げず、到達しないことを根拠に、上げない理由と次に見直す時点を記録する。
