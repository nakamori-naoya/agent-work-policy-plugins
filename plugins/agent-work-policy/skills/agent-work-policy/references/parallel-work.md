# 並行作業の実行資源

複数の作業場所を並行で使う前に読む。worktreeで分かれるのはGitの作業fileだけであり、検証が使う実行資源は分かれない。この資料は、並行で `start` してよいかを判断するためにある。

## worktreeの外で共有されるもの

検証commandは、しばしばrepositoryの外にある資源を名前で指す。container project名、公開port、named volume、DBとそのschema、固定pathのcacheやsocketがそうである。名前が設定fileに固定されていれば、どのworktreeから起動しても同じ資源に当たる。ある作業場所の検証が資源を作り直すと、別の作業場所の検証や、利用者が手元で動かしている開発環境まで巻き込む。

## 始める前に確かめること

並行で始める前に、検証command（policyの `verification.commands` と、repositoryが完了判定に使う入口）を読み、それが起動、作り直し、削除する資源と、その名前がどこで決まるかを確かめる。名前を作業場所ごとに変えられるなら、変えた名前で起動する。変えられない資源があれば、その資源を使う検証は直列にし、並行にするのはそれに触れない作業だけにする。

名前を変えたつもりでも、検証の途中で別の道具が固定名の資源を呼ぶことがある。compose fileの依存関係や、検証toolが内部で起動する補助containerがその例である。確かめるのは起動の入口だけでなく、検証が実際に触れる資源の全体である。

## 判断例

ある案件では、compose fileに `name:` が固定されていた。並行の作業者は `-p` でproject名を変えて起動したが、検証の中のschema検査toolが依存関係を通じて固定名のstackへ接続し、利用者の開発DB（tmpfs）を作り直してデータを消した。検証の全体を読んでいれば、そのtoolを使う検証は直列にすると判断できた。

外部資源を持たない純粋なlibraryでは、この確認は空で終わる。それで害は無い。
